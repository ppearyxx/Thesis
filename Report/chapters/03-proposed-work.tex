The System Context Diagram provides a high-level overview of the Adnexio platform, defining its boundaries and illustrating the primary interactions between the system, its users (actors), and other external systems. It treats the platform as a single entity, focusing on its external relationships rather than its internal technical architecture.

\subsection{External Actors}
The diagram identifies three main types of external actors who interact with the platform:
\begin{itemize}
    \item \textbf{Guest User:} An unregistered visitor who can interact with the platform's public-facing features, primarily the Browsing Domain.
    \item \textbf{Essential / Elite User:} A registered member who is the primary consumer of the service. They interact with core domains such as User Management, Browsing, and Booking \& Itinerary.
    \item \textbf{Admin / Concierge:} An internal team member responsible for managing the platform. They interact with the system through the dedicated Admin \& CMS Domain.
\end{itemize}
\subsection{External Systems}
The Adnexio platform relies on several external, third-party systems to provide its full range of functionality:
\begin{itemize}
    \item \textbf{Stripe Payments:} An external payment gateway that integrates with the Payments Domain to handle all financial transactions.
    \item \textbf{Vendor APIs (PlatinumList, SevenRooms):} External partner systems that provide an inventory of third-party experiences. These are connected to the Booking \& Itinerary Domain to facilitate real-time booking.
    \item \textbf{Resend - Emailing:} A dedicated emailing service that integrates with the Notification \& Communication Domain to send transactional emails and alerts to users.
    \item \textbf{OpenAI - GPT Suggestions:} The external AI service that provides large language model capabilities to the AI Recommendation Domain for generating personalized suggestions.
\end{itemize}
The diagram also introduces our approach to Domain-Driven Design (DDD), which organizes the platform's complex business logic into the following manageable domains and subdomains:
\begin{itemize}
    \item \textbf{Booking Management:} This domain is central to the user journey. The Booking Creation subdomain handles the initiation of new reservations, while Itinerary Management structures more complex, multi-part plans. The Notifications subdomain is responsible for all booking-related communications, such as confirmations and reminders.
    \item \textbf{Payments:} This domain manages all financial transactions. Payment Processing facilitates secure payment collection via Stripe, and the Refunds subdomain manages the return of funds for cancellations or other adjustments.
    \item \textbf{User Management:} This domain handles all aspects of the user lifecycle. Authentication controls the login and signup flows, and Profile Settings manages user-specific data like preferences, contact information, and membership tier.
    \item \textbf{AI Features:} This domain powers the platform's intelligence. The Recommendations subdomain generates AI-driven suggestions based on user data, while the Chatbot Interaction subdomain provides the interface for conversational support and planning.
    \item \textbf{Admin Tools:} This domain provides the necessary tools for the internal team. Content Creation allows staff to create and edit experiences, and the Analytics subdomain offers reporting tools for tracking platform activity and engagement.
\end{itemize}
\section{System Architecture Design}
\thesisfigure{ch3-system-architecture-design.png}{System Architecture              
  Design}{System Architecture Design}{}{system-architecture-design}
Based on the system architecture diagram (Figure~\ref{fig:system-architecture-design}) , the platform's core architecture can be broken down into three main areas: Applications, Admin Stack, and Infrastructure. Each area contains specialized services that work together to deliver a seamless and robust user experience.
The Applications layer serves as the primary entry point for our members. It consists of two native mobile apps, one for iOS and one for Android, which are responsible for the entire user-facing experience. These applications handle fetching all necessary data for browsing experiences and submitting booking requests to our backend. To simplify development and ensure consistency, both apps communicate exclusively with a central Next.js API Host. This API serves as a dedicated gateway for the mobile applications, simplifying the client-side logic by taking in straightforward requests and then handling the complex task of communicating with multiple backend services to fulfill them.
The Infrastructure layer is the core of our service delivery, containing all the backend services that power the platform. When a request is made from the mobile app, the Next.js API first validates the user's session and permissions with our Auth service, which handles Role-Based Access Control (RBAC). All core business data, such as user information, booking details, and preferences, is stored and managed in our Postgres Database. For payments, the API integrates with Stripe Payments to create payment intents and securely process transactions. Upon successful payment, Stripe sends webhook updates back to our database to confirm the transaction. To enhance personalization, the API also communicates with GPT-4o to perform AI-driven actions, such as generating tailored experience recommendations for users. Finally, our Email service is triggered by events like new bookings or successful payments to send out notifications, receipts, and alerts to members.
The Admin Stack is a separate but vital component for managing the platform's operations. Internal teams use the Medusa Admin Dashboard to perform a variety of administrative actions, including customer management and experience curation. The dashboard interacts with the Medusa.js API, which functions as our core e-commerce engine. A key feature of this stack is its ability to create a diverse marketplace; the Medusa.js API manages both our own first-party experiences and integrates with external Vendor APIs, such as PlatinumList and SevenRooms, to syndicate and manage third-party offerings.

Utilizing the Workflows SDK, this layer abstracts complex business logic away from the API routes. It acts as an orchestration engine, coordinating multi-step operations (such as "Complete Order" or "Process Return") to ensure transactional integrity before passing data down to the domain modules.
    \item The Module Layer (Domain Isolation) The foundation of the architecture is the Modules layer, which encapsulates specific data models and utilities. This layer is bifurcated into\textbf{ two distinct categories:}
    \begin{itemize}
        \item Commerce Modules: These modules manage the core e-commerce domains. As illustrated by the icons in the diagram, specific modules are dedicated to Product Management, Cart Operations, Customer Profiles, and Pricing Strategies. Each module operates in isolation, preventing domain coupling.
        \item Infrastructure Modules: Running parallel to the commerce logic, these modules handle system-level operations. This includes the Workflow Engine for state management, Caching services for performance, and Event buses for asynchronous communication. These infrastructure modules act as the interface between the application logic and external services (such as the database or third-party APIs).
    \end{itemize}
\end{enumerate}

\section{User Roles \& Permissions}
\input{tables/user-roles}
In (Table~\ref{tab:user-roles}) User Roles \& Permissions, Adnexio platform employs a Role-Based Access Control (RBAC) model to manage user permissions and tailor the experience to different user types. The system defines four distinct roles Guest, Essential, Elite, and Administrator each with a specific set of capabilities and access levels designed to serve their unique needs within the platform's ecosystem.

\textbf{Guest User}
The Guest User role is designed for prospective members exploring the platform. Guests have limited, read-only access, with the ability to browse standard offers and experiences before committing to a sign-up. To perform any transactional actions, such as making a booking, a Guest must register. Upon registration or the first booking, their account is automatically upgraded to the Essential tier.

\textbf{Essential User}
The Essential User represents the standard, self-service membership tier for everyday users and casual luxury explorers. Following a self-service sign-up, Essential members gain instant access and operate on a pay-per-experience pricing model. They can perform manual bookings for standard venues, typically requiring a two-to-three-day lead time, and receive general support via chat or email. Personalization for this tier is based on basic profile data and stated preferences.

\textbf{Elite User}
The Elite User is the premium tier for affluent clients seeking a high-touch, fully managed luxury experience. Access to this tier is exclusive, requiring an application or invitation and subsequent approval. The pricing model consists of an annual membership fee in addition to per-experience costs. Elite members are distinguished by access to a dedicated 24/7 lifestyle assistant who can handle bookings and curate experiences on their behalf, securing access to high-demand venues with same-day or short-notice availability. This tier benefits from advanced personalization through a combination of AI and human-curated recommendations and enjoys VIP access, exclusive privileges, and a high degree of experience customization.

\textbf{Administrator}
The Administrator is an internal, back-office role with comprehensive oversight and control of the entire platform. Administrators have privileged access to all platform functionalities, including both the Essential and Elite user views. Their primary responsibilities include overseeing all in-app payments, processing manual transactions, sending custom notifications to members, and managing the curated catalogue of experiences.

\section{User Registration Flow}
The Adnexio platform implements a three-tiered access system which are Guest, Essential, and Elite. Each with distinct registration and authorization flows managed through Supabase Auth and the Next.js API layer. This stratified architecture ensures users receive immediate provisioning of appropriate permissions and data access through Row-Level Security (RLS) policies enforced at the PostgreSQL database level.

\subsection{Guest User Flow (Anonymous Access)}
The Guest flow enables rapid, frictionless platform exploration, allowing prospective members to browse available experiences without requiring upfront registration commitment.

\textbf{Process Flow:}
\begin{enumerate}
    \item Session Initiation: The mobile application (Expo App) establishes an anonymous session by invoking signInAnonymously() through the Supabase client SDK.
    \item Authentication and Token Generation: Supabase Auth provisions an ephemeral user record and issues a JSON Web Token (JWT) for session management.
    \item Client-Side Session Management: The JWT is securely persisted on the client device, granting temporary, read-only access to the Browsing Domain. This restricted access state corresponds to users who select "Continue as Guest" on the application's welcome screen.
\end{enumerate}

\subsection{Essential User Flow (Standard Registration)}
The Essential tier represents the platform's standard registration pathway, providing authenticated users with permanent access to core platform functionality through a self-service onboarding process. \\
\textbf{Process Flow:}
\begin{enumerate}
    \item Registration Initiation: Users submit email credentials and a secure password through the mobile application interface, triggering a call to Supabase.signUp().
    \item Email Verification: Supabase dispatches a verification email containing a unique confirmation link. This verification step validates user identity and mitigates fraudulent account creation.
    \item Account Activation: Upon clicking the verification link, the user's authentication status is updated to "verified" within the Supabase authentication database.
    \item Profile Provisioning: The system automatically generates a corresponding user profile record with Essential role assignment, unlocking access to core features including experience booking and personalized recommendations.
\end{enumerate}

\subsection{Elite User Upgrade Flow (Invitation and Payment)}
Elite status represents a premium tier requiring application-based approval and subscription payment, processed through the Medusa e-commerce backend to ensure secure financial transaction handling. \\
\textbf{Process Flow:}
\begin{enumerate}
    \item Upgrade Initiation: Authenticated Essential users request tier elevation by selecting "Upgrade to Elite" within the application interface.
    \item Invitation Generation: The application triggers a Next.js API endpoint that interfaces with the Medusa API, specifically invoking the invite.createInvite service to manage subscription product logic and pricing tiers.
    \item Payment Processing: Medusa orchestrates the payment workflow through Stripe's payment gateway, collecting either annual or monthly recurring subscription charges as configured for Elite membership.
    \item Role Elevation: Upon successful payment confirmation via Stripe webhook, the user's role assignment in the Supabase database is automatically elevated to Elite status. This promotion grants immediate access to premium features including VIP experiences, priority booking privileges, and dedicated concierge services.
\end{enumerate}

\section{User Authentication and Authorization}
\subsection{Authentication flow}
The authentication process for the Adnexio platform is handled by \textbf{Supabase Auth}, which manages user sessions, password hashing, and token issuance. This streamlines development by leveraging a managed, secure, and scalable authentication service. \\
JWT Implementation: The system is built on a JSON Web Token (JWT) architecture. Upon successful sign-in, Supabase issues a unique JWT that is sent to the client. This token contains encrypted user claims, including the user's role (Guest, Essential, or Elite) and a unique user ID (auth.uid).
\begin{enumerate}
    \item Session Validation Chain: The Next.js API Host validates this JWT for every incoming API request. The validation process ensures that the request is authentic, confirms the user's identity, and extracts the necessary role and auth.uid claims. This serves as the first security gate.
    \item Role-Based Access Control (RBAC): The role embedded in the JWT is the core mechanism for Role-Based Access Control (RBAC). This control is enforced at two crucial layers:
    \begin{enumerate}
        \item Application Layer (Next.js): Determines which API endpoints a user can access (e.g., preventing a Guest user from calling the createBooking endpoint).
        \item Database Layer (PostgreSQL/RLS): Governs data access permissions based on the user's role and ID (defined in Section~\ref{subsection:Row-Level Security (RLS) Authorization}).
    \end{enumerate}
\end{enumerate}
\subsection{Row-Level Security (RLS) Authorization}
\label{subsection:Row-Level Security (RLS) Authorization}
Authorization determining precisely what data a user is allowed to access is strictly enforced using PostgreSQL’s Row-Level Security (RLS) feature, managed through Supabase. RLS acts as the final, critical security layer.  The implementation adheres to the following core principles to ensure complete data isolation and integrity as below
\begin{enumerate}
    \item Centralized Security Logic: RLS policies are applied directly to all production-ready database tables (e.g., experiences, bookings, user\_profiles). This ensures that security logic resides within the database itself , preventing data access bypasses even if application code is compromised (excluding the privileged administrator role).
    \item Fine-Grained Access Control: RLS policies dynamically utilize the authenticated user's ID (auth.uid()) and role, which are passed to the database via the validated JWT, to filter data at the row level. This provides tailored control for each user tier:
    \begin{enumerate}
        \item A Guest user is restricted to SELECT access only on experience rows marked as publicly browsable.
        \item An Essential user is granted SELECT, INSERT, and UPDATE access exclusively on data rows linked to their own user ID (e.g., their profile or their initiated bookings). They also retain general SELECT access to standard experiences.
        \item An Elite user receives elevated SELECT privileges to access unique inventory rows and priority status data, in addition to full control over their own data.
    \end{enumerate}
    \item Principle of Least Privilege: By enforcing RLS, the application layer is shielded from implementing complex authorization queries. The system automatically adheres to the principle of least privilege, as the database inherently restricts the data returned to precisely what the authenticated user is authorized to view.
\end{enumerate}
\section{User Onboarding and Personalization}
The user onboarding phase is a critical step in the Adnexio experience, designed to gather behavioral and preference data immediately after registration of an elite role. The data collected during this phase is instrumental in providing the foundational context required by the AI Recommendation Domain (GPT-4o) for generating personalized itineraries. The onboarding process is divided based on the user's status within the UAE market.

\subsection{Resident Onboarding Flow}
For users residing in the UAE, the system collects data related to their consistent lifestyle and location, enabling location-specific and routine-based recommendations.
\begin{itemize}
    \item Geographical Context: Collects the user's current area of residence in the UAE.
    \item Routine Analysis: Gather information on the user's "typical week," establishing patterns for leisure time, work schedules, or common weekly activities.
\end{itemize}
\subsection{Visitor Onboarding Flow}
For temporary visitors, the onboarding focuses on travel logistics and the purpose of the trip to deliver time-constrained and goal-oriented recommendations.
\begin{itemize}
    \item Origin and Duration: Collects the user's country of origin and the start/end dates of their visit to the UAE. This defines the temporal window for all future itinerary and experience searches.
    \item Trip Context: Determines the "type of trip" (e.g., business, leisure, family), which heavily influences the tone and nature of AI-generated recommendations.
    \item Service Requirements: Documents any initial pre-arrival service needs, such as:
    \begin{itemize}
        \item Airport transfers.
        \item Private driver or car rental.
        \item Booking premium hotel or villa stays.
        \item VIP event tickets.
        \item Personal assistant support during the stay.
    \end{itemize}
\end{itemize}
\subsection{Universal Personalization Inputs}
Regardless of residency status, all users must define their core interests, dietary requirements, and preferred experience pace to guide the AI assistant and human concierges effectively.
\begin{itemize}
    \item \textbf{Core Interests:} Users select categories of interest (e.g., dining, wellness, bars, safari, culture, nature, VIP sports, events, networking, private beaches). This forms the initial vector embedding for semantic comparison against the experience database.
    \item \textbf{Dietary Preferences:} Users specify any mandatory dietary restrictions or requirements, including:
    \begin{itemize}
        \item Vegetarian, Vegan, Gluten-free, Dairy-free, Halal.
        \item An "Other" field for unique or less common requirements.
    \end{itemize}
    \item \textbf{Preferred Pace:} Users define their desired itinerary pace (e.g., Relaxed, Balanced, Packed), which sets a critical constraint for the GPT-4o model when constructing daily itineraries.
\end{itemize}

\section{Product Inventory}
Following the integration of the external PlatinumList API described in Section~\ref{section:Integrate external experience to system}, the system requires a unified layer to ingest, organize, and expose all experience data both external and internal to end users. This section describes the design and architecture of the product inventory system, category management, itinerary creation workflows.

\subsection{Unified Product Inventory Architecture}
The Adnexio platform adopts a dual-stream inventory model to achieve total visibility over all service offerings. The inventory is divided into \textbf{two primary categories:} \\
\begin{enumerate}
    \item \textbf{External Experiences:} Events and activities sourced from the PlatinumList API. These are ingested, transformed, and seeded into the platform's PostgreSQL database through a dedicated data standardization pipeline, as described in Section~\ref{section:Integrate external experience to system}.
    \item \textbf{Internal Experiences:} First-party experiences created and managed directly by the Adnexio administrative team through the Medusa Admin Portal, including activities such as car rentals and per-event bookings.
\end{enumerate}
Both categories are normalized into a unified product schema within the MedusaJS backend, allowing the mobile application to consume them through a consistent API interface regardless of origin.

\subsection{Category Configuration}
Product categories are structured hierarchically and are configurable by administrators through the Categories section of the admin portal. Each category is assigned a unique handle (e.g., \texttt{/entertainment-\&-shows}, \texttt{/family-fun}), an active and public status flag, and an associated category image (uploaded as JPEG, JPG, or PNG). \\
The category image is rendered on the mobile application's Explore screen as a visual tile, enabling users to browse by thematic area. \\
The defined top-level categories include, but are not limited to: Attraction, Explore, Entertainment, Icons, Family Fun, Thrills, Playgrounds, Culture \& Art, and Discover. Sub-categories may be nested beneath these top-level entries to provide additional classification granularity.

\subsection{Tag Configuration}
Product tags are managed under the Settings > Product Tags section of the admin portal. Tags serve as a lightweight, non-hierarchical labeling mechanism that complements categories. Tags such as attraction, experiences, luxury, nature, and family are assigned to individual products and are used by the AI itinerary builder as filtering criteria when selecting relevant experiences for a generated plan.

\section{Itinerary System Design}
The Adnexio platform supports two distinct itinerary creation modalities, designed to serve different user segments and administrative needs.

\subsection{Itinerary Types}
\begin{enumerate}
    \item \textbf{Pre-Made Itineraries (Admin-Created):} Curated itinerary bundles created and published by the Adnexio administrative team. These are available to both Essential and Elite users and are discoverable through the Itinerary tab of the mobile application. Each pre-made itinerary is a structured, multi-day plan that groups a set of experiences into a single purchasable bundle.
    \item \textbf{AI Itinerary Builder (Elite User-Created):} A personalized, conversational itinerary generation feature exclusive to Elite-tier users, powered by GPT-4o. Users interact with an in-app assistant named "George" to generate a bespoke itinerary based on their travel preferences, dates, and interests.
\end{enumerate}

\subsection{Pre-Made Itinerary Design}
Administrators create pre-made itineraries through the Itineraries extension in the Medusa Admin Portal. The creation workflow consists of the following components:
\begin{enumerate}
    \item \textbf{Basic Information:} The itinerary title, a cover image, a timeframe (number of days), a short subtitle description, and assigned categories and tags.
    \item \textbf{Itinerary Days \& Experiences:} A day-by-day slot builder in which administrators assign specific experience products to each day. Each slot specifies the experience product ID, the slot type (Internal Product or External/Optional), and a variant reference at checkout. Administrators may designate specific slots as optional, allowing users to customize the itinerary at the point of booking.
\end{enumerate}
Completed itineraries may be saved as a Draft or published immediately. Upon publication, the itinerary becomes visible in the mobile application's pre-made itinerary discovery section, where users may add the entire bundle to their cart in a single action.

\subsection{AI Itinerary Builder Design}
\label{subsection: AI Itinerary Builder Design}
The AI Itinerary Builder implements a structured session-based workflow to generate personalized day-by-day plans for Elite users. The builder reuses the same itinerary slot endpoints defined for pre-made itineraries and invokes them programmatically as tools called by the GPT-4o model via the Vercel AI SDK. \\
\textbf{Session Flow} \\
The builder follows a \textbf{four-stage session lifecycle:}
\begin{enumerate}
    \item \textbf{Session Start:} The session is initiated when the user opens the AI builder interface.
    \item \textbf{User Onboarding Status Check:} The system retrieves the user's onboarding profile from the database, extracting stored preferences including travel dates, user interests, and preferred pace. If the onboarding data is incomplete, the assistant prompts the user to provide the missing information.
    \item \textbf{Confirm \& Update Travel Dates and Preferred Pace:} The assistant confirms the user's intended travel dates through a structured validation step. Dates are classified into one of four states: past dates (rejected), present dates (accepted with a warning), valid future dates (accepted), or ambiguous dates (clarified through follow-up). The user also selects or confirms their preferred itinerary pace, which directly controls the number of activities scheduled per day:
    \begin{itemize}
        \item \textbf{Relaxed:} 3 activities per day
        \item \textbf{Balanced:} 4 activities per day
        \item \textbf{Packed:} 5 activities per day
    \end{itemize}
    \item \textbf{Itinerary Creation / Update:} The model generates a complete itinerary by querying available products filtered by the user's travel dates, selected interests, and pace. The AI selects appropriate experiences from the inventory, assigns them to time slots across each day of the trip, and returns the structured plan to the user through the chat interface. The generated itinerary is displayed as a day-by-day card list, with each slot showing the experience name, location, time range, and price in AED. Users may then add the complete AI-generated itinerary to their cart through a single ``add this itinerary to cart'' action, which invokes the same checkout flow as pre-made itineraries.
\end{enumerate}

\section{Discovery and Browsing Design}
The Discovery and Browsing module serves as the primary entry point through which users explore and locate available experiences within the Adnexio platform. It is implemented as the Explore tab, the default landing screen presented to all users upon opening the application. The interface is designed to support both directed search, where users seek a specific experience by name, and undirected discovery, where users browse by category or interest tag.

\subsection{Explore Tab Structure}
The Explore tab serves as the default landing screen of the mobile application and functions as the primary entry point through which users locate experiences within the platform. Its design is guided by a core principle: the interface must accommodate two distinct modes of user intent without forcing the user to commit to either upfront. Users who arrive with a specific experience in mind require a \textbf{directed search } mechanism, while users who arrive without a predefined goal require an \textbf{undirected discovery} surface that invites exploration by theme or interest. Rather than separating these modes into distinct screens, the Explore tab consolidates both into a single scrollable feed, allowing users to transition fluidly between targeted lookup and open-ended browsing within the same context.
\\
To support this dual-mode design, the Explore tab is composed of three vertically stacked sections arranged in descending order of interaction specificity:
\begin{enumerate}
    \item \textbf{Tag Filter Chips Row:} A horizontally scrollable row of filter chips rendered directly below the search bar. This section supports lightweight, reversible narrowing of the product feed. Tag chips are designed to be applied and dismissed with minimal friction, enabling users to progressively refine the catalog view without committing to a full category navigation.
    \item \textbf{Itinerary Entry Point Tiles:} Two fixed tiles serving as direct shortcuts into the platform's itinerary features: the AI Itinerary Builder and the Pre-Made Itinerary catalog. These tiles are intentionally positioned above the category grid to surface itinerary creation as a first-class pathway, rather than a feature buried within deeper navigation. This placement reflects the design intent that personalized itineraries are a headline capability of the platform, not a secondary concern.
    \item \textbf{Category Grid:} A grid of visually prominent category tiles positioned at the bottom of the feed. Each tile represents a broad thematic area of the catalog and is rendered with an administrator-configured cover image to support visual, image-led navigation. Tapping a tile transitions the user into a filtered product listing scoped to that category.
\end{enumerate}

\subsection{Tag-Based Filtering}
Tag-based filtering is designed as a secondary refinement layer over the default Explore feed, allowing users to narrow the catalog to a specific interest without committing to a full category navigation. Its behavior is governed by three design decisions.

First, the system enforces a single-active-tag model. Selecting a new chip automatically deactivates any previously active tag. This prioritizes predictability over expressive power: users always know which single criterion is shaping their view, and the model for switching or clearing filters remains consistent.

Second, filtered results are ranked by descending tag-match count. Because products may carry multiple tags, those sharing more tags with the user's active filter are treated as more contextually relevant and surfaced first. A user filtering by "wellness" should first encounter experiences that are most emphatically wellness-oriented, not experiences that merely happen to carry the tag.

Third, the chip row includes "all" as an explicit reset state, treating the unfiltered view as a first-class filter value rather than the absence of filtering. This keeps the interaction pattern consistent across all chip selections.

\subsection{Server-Side Search}
The search bar is designed as a server-side operation rather than a client-side filter over cached data. Dispatching each query to the backend ensures results always reflect the live product catalog, including newly added experiences and freshly synced external inventory (Section~\ref{section:Integrate external experience to system}). This aligns with the platform's broader principle that the mobile application remains a thin presentation layer over an authoritative backend.
To balance responsiveness against network cost, the search is governed by a two-tier debounce design:
\begin{enumerate}
    \item \textbf{Suggestion tier:} A short debounce window returns a lightweight list of matching experience names for inline suggestions below the search bar, providing fast feedback as the user types.
    \item \textbf{Full search tier:} A separate debounce window returns the complete matching product set for rendering in the results grid, engaged only after the user's input reaches a minimum character threshold.
\end{enumerate}
The minimum-character threshold is itself a design safeguard: short queries produce overly broad result sets that are neither useful to the user nor efficient to compute. The two tiers separate the concerns of guiding input from returning results, yielding a search experience that feels responsive while remaining economical.

\subsection{Default Product Ordering}
In the absence of a filter or search query, the Explore tab renders products in the catalog's default order. A deliberate decision was made to not apply client-side personalization to this default feed ordering that is not influenced by the user's onboarding preferences or behavioral history.

This reflects a separation between two modes of product surfacing. The Explore tab is a neutral, catalog-wide browsing surface whose ordering should be driven by administrative curation, not user-specific signals. Personalization here would introduce opacity: users would not know why certain experiences surfaced, and two users would see different views of the same catalog without a clear mental model for the divergence.

Personalization is instead concentrated in the AI Itinerary Builder (Sectio~\ref{subsection: AI Itinerary Builder Design}), where the user has explicitly invited the system to tailor output and retains visibility into the reasoning through the conversational interface. This preserves a clear distinction between browsing the catalog and receiving curated recommendations.

Each product card renders a consistent set of fields cover image, category tag label, truncated title, and starting price chosen to support rapid visual scanning while encouraging users to tap through for full detail rather than compressing a complete decision surface into each card.
\section{Booking Flow}
The booking flow defines the end-to-end journey a user takes from identifying an experience to receiving confirmation of a completed transaction. It is designed as a linear, five-stage sequence in which each stage resolves a specific decision before advancing the user to the next, supplemented by a post-transaction management surface for reviewing and acting on completed bookings.

\subsection{Booking Stages}
There are five stages. Those are designed to progressively narrow the user's commitment: from evaluating an experience, to configuring its specifics, to reviewing and paying for it, to receiving assurance that the booking is secured. The stage are including
\begin{enumerate}
    \item \textbf{Detail.} The first stage presents all information required for the user to make a booking decision in a single consolidated view: imagery, title, starting price, location, duration, capacity, restrictions, transport arrangements, and description. A key design rule at this stage is that acceptance of terms and conditions gates the primary action button. Where an experience carries mandatory terms, the user cannot advance until those terms are explicitly acknowledged, ensuring legal and operational requirements are satisfied before any configuration begins. The primary action button itself adapts its label to reflect the current state for example, indicating pending terms acceptance or unavailability for booking so that the user receives immediate feedback on why progression may be blocked.

    \item \textbf{Configuration.} The second stage adapts dynamically to the experience's pricing model, with three distinct configurations:
    \begin{itemize}
        \item \textbf{Open-Dates:} A date picker paired with a simple ticket quantity selector. No time slot is required because the experience permits flexible entry within the selected date.
        \item \textbf{Show-Time:} A date picker followed by a time slot selector, then per-category ticket quantity inputs. This configuration applies to experiences where each session has a fixed start and end time.
        \item \textbf{Rental:} A start date and end date picker, with the applicable pricing tier auto-calculated from the selected duration. A design rule governs the tier assignment: durations under one week apply the daily rate, durations between one week and one month apply the weekly rate, and durations of a month or longer apply the monthly rate.
    \end{itemize}
    This adaptive design ensures that the configuration interface exposes only the inputs relevant to the experience type, avoiding the confusion of irrelevant fields.

    \item \textbf{Cart.} The third stage introduces a persistent, multi-item cart that retains previously added experiences across the session. Users may book multiple experiences in a single transaction rather than being forced into one-at-a-time checkouts. A reservation timer is surfaced prominently, communicating the time window during which the cart's held inventory remains reserved. This design acknowledges that bookings against live inventory cannot be held indefinitely without degrading availability for other users.

    \item \textbf{Checkout.} The fourth stage is designed as an intermediate review step between the cart and the payment interface rather than an immediate transition into payment collection. It contains a consolidated summary of cart items, a security disclosure informing the user that card details are not stored on the platform, an option to return to browsing before committing, and a trust indicator confirming Stripe as the payment processor. A design rule at this stage is that free items bypass the payment interface entirely when a cart's total resolves to zero, the order is created directly without invoking the payment flow. The full payment architecture invoked from this stage is described in Section~\ref{subsection:Non-Subscription Payment Flow}.

    \item \textbf{Confirmation.} The final stage communicates the outcome of the transaction. On success, the user is presented with a confirmation screen displaying the booking summary, a notice that a confirmation email has been dispatched, and navigation actions to either continue browsing or review the new booking. On failure, the error is surfaced inline within the payment interface itself rather than through a separate failure screen, allowing the user to correct their input and reattempt payment without losing context or navigating away.
\end{enumerate}

\subsection{My Bookings}
Following a completed booking, users require a dedicated surface for reviewing, tracking, and managing their reservations over time. The My Bookings tab is designed as an authenticated-only surface, with non-logged-in users redirected on access attempts, reflecting that the contents are inherently personal and tied to an authenticated identity.

Bookings are organized into three tabs that reflect the lifecycle states most relevant to the user:
\begin{itemize}
    \item \textbf{Upcoming} Bookings that are confirmed and whose scheduled date lies in the future. These are the bookings the user needs to prepare for and act on.
    \item \textbf{Past:} Bookings whose scheduled date has already elapsed, providing a historical record of completed experiences.
    \item \textbf{Awaiting Confirmation:} Bookings in a pending state, where payment or administrative confirmation has not yet been resolved. These are isolated from the upcoming tab to prevent users from mistaking an unconfirmed reservation for a secured one.
\end{itemize}
A key design decision is that \textbf{status is derived client-side} from the booking's underlying data rather than being stored as an explicit classification. A booking whose end date has passed is treated as past regardless of its order state; an order marked pending is treated as awaiting; an order marked completed with a future end date is treated as upcoming. This derivation keeps the tab taxonomy simple and avoids the need for continuous backend status updates as dates naturally elapse.

Each booking card surfaces a consistent set of fields: experience title, location, date, booking number, guest count, status badge, optional linked itinerary name where the booking is part of a bundled plan, and a pending cancellation flag where the user has submitted a cancellation request that has not yet been processed. Bookings are sorted in \textbf{ascending order by start date}, prioritizing the most imminent reservations at the top of the list.

The separation of upcoming, past, and awaiting states, combined with derived rather than stored status, yields a booking management surface that stays accurate over time without requiring explicit lifecycle events to transition bookings between views.
