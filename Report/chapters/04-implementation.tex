\chapter{Implementation Results}

This chapter documents the practical realization of the design presented in Chapter~\ref{chapter:METHODOLOGY AND DESIGN} and the observable outcomes of that implementation. \subsection{Monorepo Structure}
\label{subsection:Monorepo Structure}
The repository follows a Turborepo layout with pnpm workspaces, organizing the codebase into three top-level directories: \texttt{apps/}, \texttt{packages/}, and \texttt{tooling/}. The structure is shown below:

This structure departs from the stock T3 Turbo reference layout in two deliberate ways. First, there are no Two structural decisions departing from the stock T3 Turbo layout. First, UI components are co-located within each app rather than shared through a ui package, because the mobile app (React Native) and the admin portal (Medusa's component system) do not share a rendering environment. Second, the admin application is excluded from the pnpm workspace and installed independently using npm (recorded as Architecture Decision Record 0002), because MedusaJS's dependency resolution expectations conflict with pnpm's strict workspace semantics.

\subsection{CI/CD Pipeline}
The CI/CD pipeline is hosted on Bitbucket Pipelines and is structured as two tracks: a pull-request pipeline and a set of branch-and-tag-triggered deployment pipelines.

On every pull request, the pipeline runs \texttt{pnpm install} followed by \texttt{pnpm audit -{}-audit-level=high} to scan for high-severity dependency vulnerabilities. Code quality enforcement (linting, type-checking, and formatting) is handled locally through Husky pre-commit hooks rather than as a CI gate.

Three deployment environments are defined — QA, UAT, and Production — each configured as a Bitbucket Deployment with its own environment variables:

\begin{itemize}
    \item \textbf{\texttt{main} branch} — auto-deploys the Next.js app to QA via Vercel, auto-applies Supabase migrations to the QA project, and exposes a manual trigger for an Expo EAS build using the \texttt{qa} profile.
    \item \textbf{\texttt{uat/v*} tags} — force-push the tagged commit to the \texttt{uat} environment branch, apply Supabase migrations to UAT, and expose a manual EAS build trigger using the \texttt{uat} profile.
    \item \textbf{\texttt{prod/v*} tags} — require a manual confirmation step, then force-push to the \texttt{prod} branch, apply Supabase migrations to Production, and expose a manual EAS build trigger using the \texttt{production} profile.
\end{itemize}

\subsection{Environment Isolation}

Three entirely separate Supabase projects — \texttt{[project]-qa}, \texttt{[project]-uat}, and \texttt{[project]-prod} — are provisioned, each with its own URL, anonymous key, service-role secret, and Postgres connection string. This guarantees that no environment can accidentally access data belonging to another.

Secrets and configuration values are managed across three layers:

\begin{itemize}
    \item \textbf{Vercel environment variables} per environment slot, for the Next.js applications.
    \item \textbf{Bitbucket repository and deployment variables}, for CI-side credentials.
    \item \textbf{EAS environment variables} per build profile, defined in \texttt{apps/expo/eas.json}.
\end{itemize}

Local development uses gitignored \texttt{.env} files copied from checked-in \texttt{.env.example} templates. No dedicated secret management service is used; the combination of these three layers covers the full surface of runtime secrets without an additional dependency.

Docker is used only as a local development dependency for running the Supabase stack (Postgres, Kong, Auth, Storage, Studio, Inbucket) via the Supabase CLI. The application services themselves are not containerized — no \texttt{Dockerfile} or \texttt{docker-compose.yml} exists at the application level. Deployment is handled by Vercel (Next.js apps), Render (MedusaJS), and EAS (mobile app).

\section{Core Module Implementation}
\subsection{Authentication and Authorization}
The authentication and authorization module is implemented on Supabase Auth, with session validation handled in the tRPC middleware layer of the Next.js API. This module realizes the design documented in Sections~\ref{section:User Registration Flow} and \ref{section:User Authentication and Authorization}.

\textbf{Guest (Anonymous) Access.} The guest flow described in Section~\ref{subsection:Guest User Flow (Anonymous Access)} is fully implemented. When a user taps "Continue as Guest" on the welcome screen, the application invokes supabase.auth.signInAnonymously() with the Guest role embedded as metadata on the created session. The user is then routed into the main browsing experience as an authenticated anonymous session. Guest users can browse the catalog and add items to the cart but cannot complete bookings or modify profile data, with these restrictions enforced through the role-permissions matrix described below. \thesisfigure{ch4-authentication-and-authorization-3.png}{Password Reset Flow}{Password Reset Flow (a) forgot-password screen, (b) reset-password screen}{}{authentication-and-authorization-3}

\textbf{JWT Validation in the Next.js API.} Session validation is implemented as a tRPC middleware layer. Each incoming tRPC request carries a bearer token in its authorization header; the \texttt{createTRPCContext} function decodes the token via \texttt{supabase.auth.getUser()} and attaches the resolved user to the request context. The \texttt{protectedProcedure} wrapper then enforces the presence of a valid user on every procedure that requires authentication, rejecting unauthenticated requests before they reach any business logic. This arrangement centralizes the authentication gate in a single layer and eliminates the need for individual procedures to re-validate the session.

\textbf{Role-Based Access Control.} The platform defines four roles through a numeric \texttt{ROLE\_ENUM}: Admin (1), Guest (2), Essential (3), and Elite (4), persisted relationally through a \texttt{roles} table joined to \texttt{users} via a \texttt{user\_roles} association table. Twenty-three discrete permissions are defined in a \texttt{permissions} table and linked to roles through \texttt{role\_permissions}. This relational structure allows permissions to be adjusted without schema changes and supports the tier-specific capabilities documented in Section~\ref{section:User Roles \& Permissions}.

\textbf{Row-Level Security.} The RLS design described in Section~\ref{subsection:Row-Level Security (RLS) Authorization} is implemented selectively rather than uniformly. RLS policies are applied to four tables where user-scoped data isolation is most critical: \texttt{public\_images}, \texttt{private\_images}, \texttt{user\_roles}, and \texttt{onboarding\_stage}. For remaining tables (including \texttt{profile}, \texttt{roles}, \texttt{permissions}, \texttt{payments}, and itinerary-related tables), authorization is enforced in application code through the \texttt{protectedProcedure} wrapper combined with explicit ownership checks within individual tRPC procedures. This partial application of RLS reflects a pragmatic trade-off: tables where policy logic is straightforward and the security surface is sensitive receive RLS protection, while tables where policy expression would require complex joins or where access patterns are well-contained within application code are authorized at the application layer.

Only users in the \texttt{PASSWORD\_SET\_NOT\_ONBOARDED} state reached by Elite users after their invitation has been accepted and their initial payment completed are routed into the onboarding flow. \subsubsection{Data Storage and Completion}

Onboarding responses are persisted to a single \texttt{onboarding\_stage} table with the schema (\texttt{user\_id}, \texttt{user\_type}, \texttt{step\_data jsonb}, \texttt{completed\_at}). All preference data — interests, travel dates, dietary restrictions, preferred pace, and so on — is nested under the \texttt{step\_data} field using step-keyed sub-objects (\texttt{step1}, \texttt{step2}, \texttt{step3}). The choice of a single JSONB column rather than a normalized preferences schema reflects the exploratory nature of onboarding data in an early-stage product: the set of questions may evolve as the platform matures, and JSONB storage accommodates schema evolution without migration overhead.

Onboarding completion is tracked through a dual-signal mechanism. When the user submits the final step, the \texttt{completeOnboarding} mutation sets \texttt{onboarding\_completed\_at} on the user's profile record and writes \texttt{completed\_at} on the \texttt{onboarding\_stage} row. The user's resolved state then evaluates to \texttt{ONBOARDED}, which routes subsequent sessions directly to the main application rather than back into the onboarding flow. Every step of the onboarding flow renders a progress bar showing the user's position within the three-step sequence (e.g., ``Step 2 of 3''), providing a clear sense of progression and remaining effort. The Elite tier requires recurring subscription billing, which is implemented through a Stripe Pricing Table in conjunction with the tRPC payment router. \subsubsection{Consumption Surface}
\label{subsubsection:Consumption Surface}
On the mobile side, internal experiences surface through the same product rendering pipeline used for all catalog items. The mobile client reads the following metadata fields from the product record and uses them to shape the user interface:

\begin{itemize}
  \item \texttt{pricing\_model}: distinguishes per-event experiences from rentals, driving which booking configuration is rendered.
  \item \texttt{rental\_pricing}: exposes the three-tier price structure for rental experiences.
  \item \texttt{duration\_hours}, \texttt{venue}, \texttt{max\_capacity}, \texttt{age\_restriction}, \texttt{weight\_limit}, \texttt{additional\_restrictions}: rendered as supporting detail on the experience detail screen.
  \item \texttt{is\_sold\_out}: controls availability on the date picker; when true, the corresponding date slot is rendered as disabled.
  \item \texttt{terms\_text}: conditionally rendered as the mandatory acceptance block on the detail screen.
\end{itemize}

The experience title, base date fields, and starting price are consumed from standard Medusa product and variant fields rather than from metadata.

\textbf{Variant Modeling.} Each product variant is uniquely identified by a (show-time identifier, seat category) combination, with \texttt{show\_time\_start}, \texttt{show\_time\_end}, and \texttt{show\_time\_id} stored in variant metadata. The mobile client's \texttt{groupTimesByDate} logic reads these fields to reconstruct the date-grouped time slot picker at render time, which is how the pre-generated variants produced by the authoring form surface back to the user as a coherent date-and-time selection interface.

\textbf{Rental Duration-to-Tier Mapping.} The mobile booking screen for rental experiences implements the tier-selection rule directly: durations under seven days apply the daily tier, durations between seven and twenty-nine days apply the weekly tier, and durations of thirty days or longer apply the monthly tier. The selected tier is matched to the appropriate product variant by seat category name, and the client updates the displayed price accordingly as the user adjusts the start and end dates.

\subsubsection{Product Count Rendering}
The mobile Explore tab renders a product count on each category tile to indicate how many experiences the user will find within that category. The count is fetched through the getCategoryProductCounts procedure, which queries the number of products directly assigned to each category identifier. Categories with zero products are hidden from the Explore grid entirely, ensuring users are not led into empty category listings.

A technical note is worth recording: the count reflects direct category assignments only and does not roll up child-category counts into their parent. A parent category whose products are all assigned to its children would therefore show a count of zero even if its subtree contains many experiences.

\subsection{Cart}
\label{subsection:Cart}
The cart is a persistent, multi-item structure that retains added experiences across the session and across app restarts. Figure~\ref{fig:cart} shows the cart screen with a representative multi-item booking.

\thesisfigure{ch4-cart.png}{Cart screen showing multi-item booking with reservation timer}{Cart screen showing multi-item booking with reservation timer}{}{cart}

The cart implementation has three key characteristics:
\begin{enumerate}
  \item \textbf{Persistent identity.} The cart identifier is stored in the device's asynchronous storage under a namespaced key. A user who closes and reopens the application returns to the same cart with the same held items, rather than losing state on every app lifecycle event.
  \item \textbf{Multi-item composition.} The cart is structured as a typed array of line items, each carrying its own metadata payload booking date, guest count per category, and special requests. Users may compose a trip of several experiences and check out in a single transaction, as designed in Section~\ref{subsection:Booking Stages}.
  \item \textbf{Reservation timer.} A fifteen-minute countdown begins when the first item is added to the cart:
  \begin{enumerate}
    \item The timer ticks once per second and renders prominently at the top of the cart screen.
    \item On expiry, the cart is cleared, a new empty cart is provisioned, and a toast notifies the user that items have been released.
    \item The timer's start timestamp is persisted per cart, so the countdown survives app restarts a user who reopens with three minutes remaining sees three minutes remaining, not a reset clock.
  \end{enumerate}
\end{enumerate}

\subsection{Checkout}
The checkout screen is the intermediate review step between the cart and the Stripe PaymentSheet, implementing the design rationale documented in Section~\ref{subsection:Booking Stages}.
The checkout screen has two responsibilities:
\begin{enumerate}
  \item \textbf{Review surface.} Before committing to payment, the screen presents:
  \begin{itemize}
    \item A consolidated summary of all line items with unit prices, quantities, configured dates, and captured special requests.
    \item A security disclosure confirming that card details are encrypted and not stored on the platform.
    \item A "browse more experiences" link allowing the user to return to the Explore tab.
    \item A Stripe trust indicator at the foot of the summary.
  \end{itemize}
  \item \textbf{Payment initiation.} Tapping the "Pay" button triggers the payment flow documented in Section~\ref{subsubsection:One-Time Experience Purchases}. The cart is split by payment type, a Medusa payment collection is created, and the Stripe PaymentSheet is initialized and presented. Detailed payment architecture is documented there rather than duplicated here.
\end{enumerate}

\subsection{Confirmation}
The confirmation stage communicates the outcome of the transaction and provides navigation actions for continuing on the platform. Figure~\ref{fig:confirmation} shows the confirmation screen as presented after a successful booking.

\thesisfigure{ch4-confirmation.png}{Order confirmation screen}{Order confirmation screen}{}{confirmation}

The confirmation stage is composed of three elements:

\begin{enumerate}
  \item \textbf{Success presentation.} On successful payment, the user is routed to a dedicated confirmation screen containing:
    \begin{itemize}
      \item A success badge and status title (either ``payment successful'' or ``reservation successful'' depending on the order type).
      \item A booking summary enumerating the purchased line items.
      \item A notice confirming that a confirmation email has been dispatched.
      \item Two navigation actions: ``continue browsing'' (returns to Explore) and ``view my bookings'' (routes to My Bookings).
    \end{itemize}

  \item \textbf{Confirmation email dispatch.} Order-placement emails are dispatched through the Medusa backend's notification system (triggered by \texttt{order.placed} events), not through this monorepo's Resend integration. The Resend integration handles a dedicated subset of transactional emails --- subscription cancellation, booking cancellation, and the Elite welcome email. This split reflects the architectural boundary between the commerce engine (order lifecycle) and the application layer (user-account and subscription events).

  \item \textbf{Failure handling.} Payment failures are rendered inline within the Stripe PaymentSheet itself rather than surfaced through a dedicated failure screen, allowing the user to correct their input and reattempt payment without losing context. This is a deliberate design choice documented in Section~\ref{subsection:Booking Stages} and is visible in Figure~\ref{fig:confirmation} from Section~\ref{subsubsection:One-Time Experience Purchases}.
\end{enumerate}

\subsection{My Bookings}

The booking-management surface has five key characteristics:

\begin{enumerate}
  \item \textbf{Tab structure with derived status.} Bookings are organized into three tabs --- Upcoming, Past, and Awaiting Confirmation --- with status derived client-side from the booking's underlying data:
    \begin{itemize}
      \item If the end date has elapsed $\rightarrow$ Past.
      \item If the order status is \texttt{pending} $\rightarrow$ Awaiting Confirmation.
      \item If the order status is \texttt{completed} with a future end date $\rightarrow$ Upcoming.
    \end{itemize}

  \item \textbf{Booking card.} Each card renders a consistent set of fields: experience title, location, configured date range, booking number, guest count, and a status badge. Where applicable, two additional indicators are rendered:
    \begin{itemize}
      \item The linked itinerary name, prefixed ``Part of `\ldots' itinerary'', where the booking was made as part of an itinerary bundle.
      \item A pending cancellation flag, where the user has submitted a cancellation request that has not yet been processed.
    \end{itemize}

  \item \textbf{Pull-to-refresh.} The bookings list supports pull-to-refresh, invoking the underlying tRPC query's refetch mechanism. This is particularly important for the Awaiting Confirmation tab, where administrator actions drive resolution.

  \item \textbf{Booking detail.} Tapping any card navigates to the Booking Detail screen, which surfaces the full booking context along with two user actions:
    \begin{itemize}
      \item \textbf{Add-to-calendar affordance} with native calendar integration. The resulting calendar event carries the experience title, date range, location, and notes, followed by a success alert. Long-span rentals over thirty days are excluded from calendar write eligibility.
      \item \textbf{Cancel booking action.}
    \end{itemize}

  \item \textbf{Cancellation flow.} The cancel booking action opens a confirmation modal. On confirmation:
    \begin{itemize}

      \item The mutation targets Medusa's V2 cancellation endpoint, routing the cancellation to the administrative refund-management surface documented in Section~\ref{subsubsection:Refund Management}.

\section{AI Itinerary Builder Implementation}
\subsection{Session Entry and Conversational Flow}
Elite users enter the builder through two affordances on the mobile application: the "create itinerary" tile on the Browse tab, and a floating AI button on the main surface. Non-Elite users are routed to the tier upgrade prompt instead. The chat modal is titled "ask george" and opens with the assistant message "welcome to your ai travel assistant! when would you like to travel?".

The four-stage conversational flow designed in Section~\ref{subsection:AI Itinerary Builder Design} is implemented as a six-stage mandatory sequence encoded in the system prompt: session start → date validation → pace confirmation → guided exploration → itinerary creation → booking completion. The flow is prompt-enforced rather than state-machine-enforced; at the configured temperature of 0.3 the model follows the prescribed sequence reliably in practice."Ask George" chat interface mid-conversation
\thesisfigure{ch4-session-entry-and-conversational-flow.png}{"Ask George" chat interface mid-conversation}{"Ask George" chat interface mid-conversation}{}{session-entry-and-conversational-flow}

\subsection{Personalization Inputs and Tool-Driven Generation}
The builder is powered by GPT-4o via the Vercel AI SDK with a maximum of nine tool-call steps per response. Personalization is assembled at request time: the mobile client transmits the user's onboarding profile with each message, and the server bakes the user's interests, trip type, and dietary preferences (Section~\ref{subsection:User Onboarding and Personalization}) directly into the per-request system prompt.
GPT-4o is given access to nine registered tools covering four capabilities:

\begin{enumerate}
  \item \textbf{Profile read/write} --- \texttt{get\_user\_travel\_dates}, \texttt{update\_user\_travel\_dates}, \texttt{get\_user\_preferred\_pace}, \texttt{update\_user\_preferred\_pace}.
  \item \textbf{Catalog query} --- \texttt{get\_available\_products} filters the Medusa catalog by dates, interests, and pace.
  \item \textbf{Itinerary assembly} --- \texttt{create\_itinerary\_from\_products}, \texttt{update\_itinerary}, \texttt{publish\_itinerary}.
  \item \textbf{Knowledge retrieval} --- \texttt{search\_knowledge\_base} performs semantic vector search over user-uploaded documents.
\end{enumerate}

\subsection{Generated Itinerary Output and Cart Integration}
The itinerary is delivered through streamed markdown in the chat, while the day-by-day card layout is rendered from the structured tool-result object returned by \texttt{create\_itinerary\_from\_products}. Titles, times, and prices are parsed from the tool's JSON output rather than from free-text prose, avoiding the brittleness of prose-parsing while preserving the conversational feel.

\thesisfigure{ch4-generated-itinerary-output-and-cart-integration.png}{Generated itinerary with day cards and ``add this itinerary to cart'' action}{Generated itinerary with day cards and ``add this itinerary to cart'' action}{}{generated-itinerary-output-and-cart-integration}

On user confirmation, \texttt{publish\_itinerary} executes a three-step flow:
\begin{enumerate}
  \item \textbf{Publish} — transition the itinerary from draft to published.
  \item \textbf{Verify availability} — confirm each line item is still bookable.
  \item \textbf{Add to cart} — post each line item to Medusa's /store/carts/{cartId}/line-items endpoint with metadata tying it back to the itinerary.
\end{enumerate}

This reuses the \textbf{same Medusa endpoint} as the manual booking path (Section~ref{subsection:Cart}), so AI-generated itineraries flow through the identical cart → checkout → Stripe → order pipeline as any other booking.

\section{AI Itinerary Builder Evaluation}
To empirically ground the builder's value claim, a comparative user study was conducted against the manual booking flow.

\subsection{Methodology}
\label{subsection:Methodology}
Five participants were instructed to plan a three-day "Romantic Anniversary" trip to Dubai. The trip planning task required specific inclusions for each day: one evening activity with a view, one luxury dinner, and one afternoon relaxation activity. Participants sequentially utilized two distinct planning methods: manual selection through the Explore tab and the AI builder using a natural-language prompt.

Four quantitative metrics were recorded for each method: total completion time, incidence of scheduling conflicts, presence of human errors (incorrect date or price), and the number of prompt retries (applicable only to the AI method). Furthermore, participants provided a 1–10 rating for each method regarding ease of use, confidence, and perceived speed.
\input{tables/ai-vs-manual-itinerary}

The AI builder delivered an \textbf{87.8\% reduction in median completion time} and a \textbf{100\% reduction in scheduling conflicts} against the manual method, while raising perceived ease of use by \textbf{59\%}. The time advantage stems from processing all scenario constraints, dates, interest categories, pace, and pairing coherence in a single streamed response, whereas the manual method requires sequential discovery, filtering, and verification of each experience. The conflict-reduction advantage stems from scheduling against validated product variants with enforced time boundaries, which structurally precludes overlaps rather than discouraging them.
