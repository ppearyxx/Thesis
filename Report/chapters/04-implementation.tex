\chapter{Implementation Results}

This chapter documents the practical realization of the design presented in Chapter~\ref{chapter:METHODOLOGY AND DESIGN} and the observable outcomes of that implementation. Screenshots, file structures, and concrete configuration details are presented here to demonstrate that each designed component was built in a working form, and that the platform operates end-to-end as intended.

\section{Development Environment Setup}

\subsection{Monorepo Structure}
The repository follows a Turborepo layout with pnpm workspaces, organizing the codebase into three top-level directories: \texttt{apps/}, \texttt{packages/}, and \texttt{tooling/}. The structure is shown below:

First, UI components are co-located within each app rather than shared through a ui package, because the mobile app (React Native) and the admin portal (Medusa's component system) do not share a rendering environment. Second, the admin application is excluded from the pnpm workspace and installed independently using npm (recorded as Architecture Decision Record 0002), because MedusaJS's dependency resolution expectations conflict with pnpm's strict workspace semantics.

\subsection{CI/CD Pipeline}
The CI/CD pipeline is hosted on Bitbucket Pipelines and is structured as two tracks: a pull-request pipeline and a set of branch-and-tag-triggered deployment pipelines.

On every pull request, the pipeline runs \texttt{pnpm install} followed by \texttt{pnpm audit -{}-audit-level=high} to scan for high-severity dependency vulnerabilities. Code quality enforcement (linting, type-checking, and formatting) is handled locally through Husky pre-commit hooks rather than as a CI gate.

Three deployment environments are defined — QA, UAT, and Production — each configured as a Bitbucket Deployment with its own environment variables:

\begin{itemize}
    \item \textbf{\texttt{main} branch} — auto-deploys the Next.js app to QA via Vercel, auto-applies Supabase migrations to the QA project, and exposes a manual trigger for an Expo EAS build using the \texttt{qa} profile.
    \item \textbf{\texttt{uat/v*} tags} — force-push the tagged commit to the \texttt{uat} environment branch, apply Supabase migrations to UAT, and expose a manual EAS build trigger using the \texttt{uat} profile.
    \item \textbf{\texttt{prod/v*} tags} — require a manual confirmation step, then force-push to the \texttt{prod} branch, apply Supabase migrations to Production, and expose a manual EAS build trigger using the \texttt{production} profile.
\end{itemize}

\subsection{Environment Isolation}

Three entirely separate Supabase projects — \texttt{[project]-qa}, \texttt{[project]-uat}, and \texttt{[project]-prod} — are provisioned, each with its own URL, anonymous key, service-role secret, and Postgres connection string. This guarantees that no environment can accidentally access data belonging to another.

Secrets and configuration values are managed across three layers:

\begin{itemize}
    \item \textbf{Vercel environment variables} per environment slot, for the Next.js applications.
    \item \textbf{Bitbucket repository and deployment variables}, for CI-side credentials.
    \item \textbf{EAS environment variables} per build profile, defined in \texttt{apps/expo/eas.json}.
\end{itemize}

Local development uses gitignored \texttt{.env} files copied from checked-in \texttt{.env.example} templates. No dedicated secret management service is used; the combination of these three layers covers the full surface of runtime secrets without an additional dependency.

Docker is used only as a local development dependency for running the Supabase stack (Postgres, Kong, Auth, Storage, Studio, Inbucket) via the Supabase CLI. The application services themselves are not containerized — no \texttt{Dockerfile} or \texttt{docker-compose.yml} exists at the application level. Deployment is handled by Vercel (Next.js apps), Render (MedusaJS), and EAS (mobile app).

\textbf{JWT Validation in the Next.js API.} Session validation is implemented as a tRPC middleware layer. Each incoming tRPC request carries a bearer token in its authorization header; the \texttt{createTRPCContext} function decodes the token via \texttt{supabase.auth.getUser()} and attaches the resolved user to the request context. The \texttt{protectedProcedure} wrapper then enforces the presence of a valid user on every procedure that requires authentication, rejecting unauthenticated requests before they reach any business logic. This arrangement centralizes the authentication gate in a single layer and eliminates the need for individual procedures to re-validate the session.

\textbf{Role-Based Access Control.} The platform defines four roles through a numeric \texttt{ROLE\_ENUM}: Admin (1), Guest (2), Essential (3), and Elite (4), persisted relationally through a \texttt{roles} table joined to \texttt{users} via a \texttt{user\_roles} association table. Twenty-three discrete permissions are defined in a \texttt{permissions} table and linked to roles through \texttt{role\_permissions}. This relational structure allows permissions to be adjusted without schema changes and supports the tier-specific capabilities documented in Section~3.3.

\textbf{Row-Level Security.} The RLS design described in Section 3.5.2 is implemented selectively rather than uniformly. RLS policies are applied to four tables where user-scoped data isolation is most critical: \texttt{public\_images}, \texttt{private\_images}, \texttt{user\_roles}, and \texttt{onboarding\_stage}. For remaining tables (including \texttt{profile}, \texttt{roles}, \texttt{permissions}, \texttt{payments}, and itinerary-related tables), authorization is enforced in application code through the \texttt{protectedProcedure} wrapper combined with explicit ownership checks within individual tRPC procedures. This partial application of RLS reflects a pragmatic trade-off: tables where policy logic is straightforward and the security surface is sensitive receive RLS protection, while tables where policy expression would require complex joins or where access patterns are well-contained within application code are authorized at the application layer.

\subsection{User Onboarding and Personalization}
\subsubsection{Tier Routing and Entry Conditions}
The routing logic at the application entry point distinguishes between user states and dispatches users to the appropriate post-authentication surface. Only users in the \texttt{PASSWORD\_SET\_NOT\_ONBOARDED} state reached by Elite users after their invitation has been accepted and their initial payment completed are routed into the onboarding flow. Essential users, already-onboarded Elite users, and Guest sessions are routed directly to the main browsing experience. This implementation confirms the design claim that onboarding is Elite-exclusive, with no Essential-tier onboarding path present in the codebase.

The flow opens with an Elite welcome screen that introduces the purpose of onboarding and offers a "skip for now" affordance. Upon proceeding, the user is presented with the residency question resident or visitor which determines the branch of onboarding that follows. Figure~\ref{fig:tier-routing-and-entry-conditions-1} shows the Elite welcome screen and the residency selection step.
\thesisfigure{ch4-tier-routing-and-entry-conditions-1.png}{Elite Onboarding Entry Point}{Elite Onboarding Entry Point \\ (a) welcome screen with ``start onboarding'' and ``skip for now'' options, (b) residency selection step}{}{tier-routing-and-entry-conditions-1}

\subsubsection{Resident Branch}
Users who select "resident" are presented with a two-step questionnaire focused on establishing their consistent lifestyle patterns within the UAE. Step 2 collects their area of residence, typical weekly routine, lifestyle priorities (e.g., dining, wellness, fitness, private events), types of assistance they seek from the platform, and planning preferences. Step 3 collects dietary needs, preferred communication method, and whether the user wishes to receive curated weekly suggestions. Figure~\ref{fig:resident-branch} shows the resident onboarding screens.

\thesisfigure{ch4-resident-branch.png}{Resident Onboarding Questionnaire}{Resident Onboarding Questionnaire \\ (a) step 2: location, typical week, lifestyle priorities, \\ (b) step 3: dietary, communication, weekly suggestions}{}{resident-branch}

\subsubsection{Visitor Branch}
Users who select "visitor" are presented with a structurally different questionnaire focused on trip logistics rather than routine. Step 2 collects the location and travel dates of their visit, their core interests (dining, wellness, culture, nature, VIP, sports, events, networking, private beaches), their preferred itinerary pace, and any pre-arrival services required (airport transfers, private driver, hotel booking, VIP event tickets, personal assistant). Step 3 collects dietary preferences and any additional requirements.

The visitor branch differs from the resident branch not only in the questions asked but in the underlying data model captured. The two branches write distinct key sets under the \texttt{step\_data} JSONB column, reflecting the different temporal and contextual concerns of each user type. Figure~\ref{fig:visitor-branch} shows the visitor onboarding screens.

\thesisfigure{ch4-visitor-branch.png}{Visitor Onboarding Questionnaire}{Visitor Onboarding Questionnaire \\ (a) step 2: travel dates, interests, pace, services, \\ (b) step 3: dietary preferences and additional requirements}{}{visitor-branch}

\subsubsection{Data Storage and Completion}

Onboarding responses are persisted to a single \texttt{onboarding\_stage} table with the schema (\texttt{user\_id}, \texttt{user\_type}, \texttt{step\_data jsonb}, \texttt{completed\_at}). All preference data — interests, travel dates, dietary restrictions, preferred pace, and so on — is nested under the \texttt{step\_data} field using step-keyed sub-objects (\texttt{step1}, \texttt{step2}, \texttt{step3}). The choice of a single JSONB column rather than a normalized preferences schema reflects the exploratory nature of onboarding data in an early-stage product: the set of questions may evolve as the platform matures, and JSONB storage accommodates schema evolution without migration overhead.

Onboarding completion is tracked through a dual-signal mechanism. When the user submits the final step, the \texttt{completeOnboarding} mutation sets \texttt{onboarding\_completed\_at} on the user's profile record and writes \texttt{completed\_at} on the \texttt{onboarding\_stage} row. The user's resolved state then evaluates to \texttt{ONBOARDED}, which routes subsequent sessions directly to the main application rather than back into the onboarding flow. Every step of the onboarding flow renders a progress bar showing the user's position within the three-step sequence (e.g., ``Step 2 of 3''), providing a clear sense of progression and remaining effort. \subsubsection{Elite Subscription Billing}
The Elite tier requires recurring subscription billing, which is implemented through a Stripe Pricing Table in conjunction with the tRPC payment router. The mobile client renders a plan selection screen that offers both monthly and annual billing intervals, each backed by a distinct Stripe price. The chosen price identifier is passed through to the subscription creation path on the backend.

The payment router implements six procedures to support the subscription surface: \texttt{getUserSubscription} and \texttt{getSubscription} for reading current state, \texttt{createCustomerSession} for initiating the Stripe Pricing Table flow, \texttt{getEliteSubscriptionPrice} for resolving the correct price identifier, \texttt{cancelSubscription} for ending an active subscription, and \texttt{createPaymentIntent} for the one-time flow described above. A subscription record is persisted to the Supabase payments table with \texttt{type = "subscription"}, capturing the Stripe customer identifier, the Stripe subscription identifier, the billing interval, and the mirrored Stripe subscription status.

\section{Product Inventory Implementation}
The product inventory module realizes the design documented in Sections 3.8, 3.9, and the inventory-related parts of Section 3.13. A structural note is important before presenting the implementation detail: the Adnexio platform is delivered as two distinct repositories the consumer-facing monorepo (containing the mobile app, the Next.js API host, and the shared packages), and a separate Medusa backend repository that contains the commerce engine and its custom admin extensions. The authoring tools for internal experiences, the PlatinumList synchronization extension, and the category management UI are implemented within the Medusa backend repository. This subsection therefore documents the inventory module from two complementary perspectives: the authoring surface (evidenced through Medusa admin screenshots) and the consumption surface (evidenced through the mobile client's consumption logic, which resides in the monorepo documented in Chapter 4.1).

\subsection{Internal Experience Management}
Internal experiences are authored through a custom admin extension within the Medusa backend, and are consumed by the mobile client as standard Medusa products carrying typed variants and metadata fields. This subsection documents both sides of that boundary.

\subsubsection{Authoring Surface}
The admin authoring form realizes the metadata schema described in Section 3.9.2. Administrators create internal experiences by filling in a structured form that captures basic information (event title, location, event date, end date), pricing configuration (base price, currency, availability, max capacity), operational constraints (duration, age restriction, weight limit), and policy text (terms and conditions, refund policy). Figure~\ref{fig:authoring-surface-1} and Figure~\ref{fig:authoring-surface-2} show the admin metadata form as it appears to the authoring user.

\thesisfigure{ch4-authoring-surface-1.png}{Internal experience metadata in Medusa admin (1)}{Internal experience metadata in Medusa admin (1)}{}{authoring-surface-1}

Two distinct pricing models are supported. The \textbf{per-event model} uses a bulk date-range generator that accepts a start date, an end date, a set of default time slots with associated capacities, and a global ticket type catalog (e.g., "Standard Admission", "Ultimate Express"). When the administrator saves, the backend pre-generates a product variant for each combination of (date, time slot, ticket type) a pattern confirmed by the mobile client's variant-grouping logic, which re-groups these pre-generated variants by date and time slot at render time. Figure~\ref{fig:authoring-surface-3} shows the per-event configuration form with the date range generator and ticket type definitions.

\thesisfigure{ch4-authoring-surface-3.png}{Per-event pricing and ticket-type configuration}{Per-event pricing and ticket-type configuration}{}{authoring-surface-3}

The \textbf{rental model} is used for asset-based services such as car rentals. The administrator configures three pricing tiers daily, weekly, and monthly and the backend auto-generates three corresponding seat-category variants upon save. The rental start window is also specified at authoring time to constrain the date range within which users may initiate a rental. Figure~\ref{fig:authoring-surface-4} shows the rental configuration form.

\thesisfigure{ch4-authoring-surface-4.png}{Rental pricing tier configuration}{Rental pricing tier configuration}{}{authoring-surface-4}

\subsubsection{Consumption Surface}
On the mobile side, internal experiences surface through the same product rendering pipeline used for all catalog items. The mobile client reads the following metadata fields from the product record and uses them to shape the user interface:

\begin{itemize}
  \item \texttt{pricing\_model}: distinguishes per-event experiences from rentals, driving which booking configuration is rendered.
  \item \texttt{rental\_pricing}: exposes the three-tier price structure for rental experiences.
  \item \texttt{duration\_hours}, \texttt{venue}, \texttt{max\_capacity}, \texttt{age\_restriction}, \texttt{weight\_limit}, \texttt{additional\_restrictions}: rendered as supporting detail on the experience detail screen.
  \item \texttt{is\_sold\_out}: controls availability on the date picker; when true, the corresponding date slot is rendered as disabled.
  \item \texttt{terms\_text}: conditionally rendered as the mandatory acceptance block on the detail screen.
\end{itemize}

The experience title, base date fields, and starting price are consumed from standard Medusa product and variant fields rather than from metadata.

\textbf{Variant Modeling.} Each product variant is uniquely identified by a (show-time identifier, seat category) combination, with \texttt{show\_time\_start}, \texttt{show\_time\_end}, and \texttt{show\_time\_id} stored in variant metadata. The mobile client's \texttt{groupTimesByDate} logic reads these fields to reconstruct the date-grouped time slot picker at render time, which is how the pre-generated variants produced by the authoring form surface back to the user as a coherent date-and-time selection interface.

\textbf{Rental Duration-to-Tier Mapping.} The mobile booking screen for rental experiences implements the tier-selection rule directly: durations under seven days apply the daily tier, durations between seven and twenty-nine days apply the weekly tier, and durations of thirty days or longer apply the monthly tier. The selected tier is matched to the appropriate product variant by seat category name, and the client updates the displayed price accordingly as the user adjusts the start and end dates.

\textbf{Terms Acceptance Gate.} The terms-acceptance gate described in Section 3.11.1 is fully implemented. When an experience's metadata includes a non-empty \texttt{terms\_text} field, the primary action button on the detail screen is disabled and its label reads ``accept terms to continue'' until the user checks the acceptance box. Once accepted, the button becomes active and its label transitions to the standard booking action.
