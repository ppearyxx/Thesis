\chapter{Implementation Results}

This chapter documents the practical realization of the design presented in Chapter~\ref{chapter:METHODOLOGY AND DESIGN} and the observable outcomes of that implementation. Screenshots, file structures, and concrete configuration details are presented here to demonstrate that each designed component was built in a working form, and that the platform operates end-to-end as intended.

\section{Development Environment Setup}

\subsection{Monorepo Structure}
The repository follows a Turborepo layout with pnpm workspaces, organizing the codebase into three top-level directories: \texttt{apps/}, \texttt{packages/}, and \texttt{tooling/}. The structure is shown below:

First, UI components are co-located within each app rather than shared through a ui package, because the mobile app (React Native) and the admin portal (Medusa's component system) do not share a rendering environment. Second, the admin application is excluded from the pnpm workspace and installed independently using npm (recorded as Architecture Decision Record 0002), because MedusaJS's dependency resolution expectations conflict with pnpm's strict workspace semantics.

\subsection{CI/CD Pipeline}
The CI/CD pipeline is hosted on Bitbucket Pipelines and is structured as two tracks: a pull-request pipeline and a set of branch-and-tag-triggered deployment pipelines.

On every pull request, the pipeline runs \texttt{pnpm install} followed by \texttt{pnpm audit -{}-audit-level=high} to scan for high-severity dependency vulnerabilities. Code quality enforcement (linting, type-checking, and formatting) is handled locally through Husky pre-commit hooks rather than as a CI gate.

Three deployment environments are defined — QA, UAT, and Production — each configured as a Bitbucket Deployment with its own environment variables:

\begin{itemize}
    \item \textbf{\texttt{main} branch} — auto-deploys the Next.js app to QA via Vercel, auto-applies Supabase migrations to the QA project, and exposes a manual trigger for an Expo EAS build using the \texttt{qa} profile.
    \item \textbf{\texttt{uat/v*} tags} — force-push the tagged commit to the \texttt{uat} environment branch, apply Supabase migrations to UAT, and expose a manual EAS build trigger using the \texttt{uat} profile.
    \item \textbf{\texttt{prod/v*} tags} — require a manual confirmation step, then force-push to the \texttt{prod} branch, apply Supabase migrations to Production, and expose a manual EAS build trigger using the \texttt{production} profile.
\end{itemize}

\subsection{Environment Isolation}

Three entirely separate Supabase projects — \texttt{[project]-qa}, \texttt{[project]-uat}, and \texttt{[project]-prod} — are provisioned, each with its own URL, anonymous key, service-role secret, and Postgres connection string. This guarantees that no environment can accidentally access data belonging to another.

Secrets and configuration values are managed across three layers:

\begin{itemize}
    \item \textbf{Vercel environment variables} per environment slot, for the Next.js applications.
    \item \textbf{Bitbucket repository and deployment variables}, for CI-side credentials.
    \item \textbf{EAS environment variables} per build profile, defined in \texttt{apps/expo/eas.json}.
\end{itemize}

Local development uses gitignored \texttt{.env} files copied from checked-in \texttt{.env.example} templates. No dedicated secret management service is used; the combination of these three layers covers the full surface of runtime secrets without an additional dependency.

Docker is used only as a local development dependency for running the Supabase stack (Postgres, Kong, Auth, Storage, Studio, Inbucket) via the Supabase CLI. The application services themselves are not containerized — no \texttt{Dockerfile} or \texttt{docker-compose.yml} exists at the application level. Deployment is handled by Vercel (Next.js apps), Render (MedusaJS), and EAS (mobile app).
