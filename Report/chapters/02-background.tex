\subsection{System Architecture}
\subsubsection{Monolithic Architecture}

Monolithic architecture refers to a traditional software design pattern in which all components of an application --- including user interface, business logic, and data access layers --- are packaged and deployed as a single (Figure~\ref{fig:monolithic-architecture}), unified unit. In this model, the application runs as one process, often supported by a single codebase and a centralized database. \cite{thalor2024monolithic} describe monolithic systems as tightly coupled, meaning that changes in one part of the application often necessitate redeployment of the entire system.

The primary advantage of monolithic architecture lies in its simplicity. It is straightforward to develop, test, and deploy, making it particularly suitable for small teams and minimum viable products (MVPs). Since all components share the same memory space and runtime environment, monolithic applications also benefit from reduced communication overhead compared to distributed systems. This architecture enables rapid iteration during early development phases, where time-to-market and cost efficiency are prioritized.

\subsubsection{Domain Driven Design (DDD)}

Domain-Driven Design (DDD) is a software engineering methodology that integrates software architecture with the business domain to address the complexity of large-scale systems. Its primary objective is to ensure that software models accurately represent business processes, thereby shifting development from a technology-oriented to a domain-oriented perspective. \cite{ozkan2025ddd}

Two foundational concepts define DDD: Ubiquitous Language and Bounded Contexts. Ubiquitous Language is a collaboratively developed vocabulary shared between developers and domain experts. By embedding this language directly into communication and source code, DDD eliminates ambiguity and strengthens the alignment between the software model and the business domain. Bounded Contexts, in contrast, establish explicit boundaries around sub-domains, each maintaining its own model and terminology. This separation reduces complexity, prevents inconsistencies, and allows development teams to focus on smaller, coherent parts of the system.

Beyond conceptual clarity, DDD offers practical architectural benefits. The separation provided by Bounded Contexts naturally aligns with modern distributed paradigms such as microservices, where autonomous and loosely coupled services are essential. This approach enables systems to evolve alongside changing business requirements while maintaining technical robustness and strategic alignment with organizational goals. \cite{ozkan2025ddd}

\subsubsection{System Context Diagram}

The System Context Diagram is rooted in Structured Analysis and Design Technique (SADT). This methodology, developed in the 1970s, aimed to create a more disciplined approach to software development. The SCD is an integral part of Data Flow Diagrams (DFDs), where it serves as the top-level, or Level 0, diagram. \cite{paloalto2025dfd}

The theoretical underpinning is that by defining the system's boundaries and external interfaces first, developers can avoid getting bogged down in internal details too early. This aligns with the principle of separation of concerns, which advocates for breaking down a complex problem into smaller, more manageable parts. By isolating the system from its environment, the SCD allows for a clear focus on the system's external behavior before delving into its internal structure. This top-down approach ensures that the system being developed is relevant and responsive to the needs of its users and the environment it operates in.

\subsubsection{Codebase Structure}

A monorepo \cite{fernandez2024monorepo} is a single, unified version-controlled repository that houses a collection of logically distinct projects. This architectural paradigm contrasts with the traditional multirepo approach, where each project resides in its own separate repository. The primary advantage of a monorepo is the simplification of dependency management and a streamlined approach to code sharing across different applications, such as a web frontend and its corresponding API.

To address the performance challenges inherent in a large monorepo, namely slow build and testing times, the build system Turborepo \cite{turborepo2025intro} is employed. Turborepo operates on two key principles: content-addressable caching and parallel task execution. Content-addressable caching ensures that if the input to a build task has not changed, the build output can be instantly retrieved from a cache, eliminating redundant computation. Parallel task execution, in turn, leverages the inherent dependencies between projects to run independent tasks concurrently, maximizing the utilization of computational resources.

The T3 Stack’s significance lies in its powerful combination of tools, which addresses common challenges in full-stack development. \subsubsection{React Native}
React Native is an open-source framework that allows developers to build mobile applications for iOS and Android using a single codebase of JavaScript and React. This approach differs from traditional native development, where separate codebases are maintained for each platform. At its core, React Native translates the JavaScript code into platform-specific UI components, providing a user experience that is visually and functionally indistinguishable from a native application. The framework's ability to reuse code across different operating systems streamlines the development process while retaining access to native APIs for performance-critical functions. It has gained widespread adoption due to its ability to offer a unified development experience and a rich ecosystem for creating high-quality mobile applications. \cite{reactnative2025intro}

\subsubsection{Expo}
Expo is a development framework built on top of React Native that simplifies mobile application development. It provides a managed workflow with pre-configured tools, over-the-air (OTA) updates, and access to a wide range of native APIs, which enables developers to rapidly prototype and deploy applications. Expo’s approach lowers the barrier to entry for mobile development by abstracting away complex native setup processes, allowing teams to focus on the application logic. \subsubsection{tRPC}
tRPC is a framework designed for building fully type-safe APIs in TypeScript applications\cite{trpc2025quickstart}. Its core innovation lies in its ability to eliminate the need for traditional API schema definitions, such as those used in REST or GraphQL, by sharing type definitions directly between the client and the server. This architectural approach ensures end-to-end type safety, which effectively mitigates common runtime errors associated with data contract mismatches and streamlines the maintenance of both frontend and backend systems. By providing developers with real-time autocompletion and compile-time error checking, tRPC significantly enhances the developer experience and accelerates the development cycle. This provides a lightweight and strongly typed communication layer that exemplifies a growing trend in modern full-stack development, prioritizing efficiency, developer experience, and system reliability. \subsection{Database \& Data Management}
\subsubsection{Supabase}
Supabase is an open-source Backend-as-a-Service (BaaS) platform that provides developers with managed PostgreSQL databases, authentication services, real-time APIs, and edge functions \cite{supabase2025architecture}. As a BaaS solution, it abstracts much of the complexity of backend development, enabling rapid prototyping and scalable application deployment without extensive server-side configuration. \subsubsection{Drizzle ORM}
Drizzle ORM \cite{drizzle2025overview} is a TypeScript-first Object-Relational Mapping (ORM) library specifically designed for relational databases. It fundamentally differs from many traditional ORMs by adopting a schema-first approach, where the database schema is defined directly within the application's code using a strongly typed API. This methodology provides developers with compile-time error checking, which significantly enhances code safety and maintainability by identifying data-related errors before the application is even executed. By providing a type-safe query builder, Drizzle ORM reduces the likelihood of runtime errors, thereby improving developer productivity and establishing a robust, predictable interface between the application and the database. This approach aligns with modern software development paradigms that prioritize static typing and early error detection to build more reliable and scalable systems.

\subsection{Development Tools}
\subsubsection{Turborepo}
Turborepo is a high-performance build system specifically designed for managing a monorepo \cite{turborepo2025intro}, which is a version-controlled repository containing multiple distinct projects. Its core function is to optimize build times by leveraging a sophisticated cache system that only executes tasks on code that has changed. ESLint  and Prettier are a complementary pair of tools used to enforce code quality and stylistic consistency. Husky acts as an automated quality gate, ensuring that essential checks such as running linters and tests are performed on every code change. This practice prevents the integration of substandard or non-compliant code into the shared repository, thereby upholding code quality and consistency throughout the entire development lifecycle.

\subsection{Development Methodology}
\subsubsection{Continuous Integration and Continuous Deployment (CI/CD)}
Continuous Integration (CI) and Continuous Deployment (CD) \cite{redhat2023cicd} is a software development methodology that aims to automate and accelerate the software development lifecycle. It represents a shift from traditional, manual processes to a more agile and efficient workflow, supported by DevOps or Site Reliability Engineering (SRE) principles. As modern applications grow in complexity, the practices of CI/CD help to streamline workflows, increase efficiency, and decrease complexity. By automating the manual human intervention traditionally required for code releases, CI/CD minimizes downtime and accelerates the delivery of new code to production.
The CI in CI/CD refers to Continuous Integration, an automated process that facilitates the frequent merging of code changes from multiple developers into a single shared repository. This addresses the problem of code conflicts that can arise when developers work in isolation and merge their work on a single "merge day".

The CD in CI/CD encompasses two related concepts: Continuous Delivery and Continuous Deployment. Both are focused on automating the later stages of the development pipeline. Continuous Delivery automates the process of releasing validated code to a repository, where it can then be manually deployed to production by an operations team. The goal is to ensure the codebase is always in a deployable state.

\subsubsection{Git Flow}
Git Flow \cite{atlassian2025gitflow}  is a structured branching model for managing source code with Git. Unlike more flexible approaches, this methodology defines a strict and prescriptive workflow by utilizing a set of dedicated, long-lived branches for different phases of development. This includes the main branch for stable, production-ready code and the develop branch, which serves as the primary integration point for all new features. 

Additionally, it uses a series of temporary branches for specific, well-defined tasks, such as feature branches for developing new functionality, release branches for preparing a new production version, and hotfix branches for addressing critical bugs in the main branch. This prescriptive, multi-branch process provides a highly organized and predictable workflow, which is particularly beneficial for larger teams and projects that require a high degree of control and a clear separation between development and deployment environments.

\subsubsection{Kanban}
Kanban \cite{planview2025kanban} is a project management methodology that provides a visual framework for organizing and managing work. It is rooted in a pull-based system where work is initiated only as capacity becomes available, ensuring a continuous and smooth workflow. The fundamental purpose of Kanban is to enhance efficiency by optimizing the flow of work and mitigating bottlenecks. This is achieved by making the workflow transparent, limiting the amount of work in progress, and continuously managing the flow of tasks through a series of defined stages. The methodology does not prescribe specific roles or time-boxed iterations, which provides a high degree of flexibility. An example of a Kanban board illustrating this workflow can be seen in (Figure~\ref{fig:kanban-board}).

\thesisfigure{ch2-kanban.png}{Example of Kanban Board}{Example of Kanban Board}{geeksforgeeks2025kanban}{kanban-board}
\textbf{Core Principles of Kanban}

The methodology is guided by four key principles designed to foster a culture of continuous, evolutionary improvement:
\begin{itemize}
  \item \textbf{Start with the existing process:} Kanban begins by implementing its practices on top of a team's current workflow without requiring an immediate, disruptive overhaul.
  \item \textbf{Agree to pursue incremental change:} It promotes small, continuous improvements rather than rapid, substantial changes. This approach minimizes resistance and encourages a gradual, evolutionary transition.
  \item \textbf{Respect existing roles and titles:} Kanban respects a team's current structure and job titles, which helps build confidence and encourages adoption of the new method without creating a sense of organizational instability.
  \item \textbf{Encourage leadership at all levels:} Leadership is not confined to a single role but is encouraged from everyone within the organization. This empowers team members to contribute to the process of continuous improvement.
\end{itemize}
