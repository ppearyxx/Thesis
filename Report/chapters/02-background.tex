\subsection{System Architecture}
\subsubsection{Monolithic Architecture}

Monolithic architecture refers to a traditional software design pattern in which all components of an application --- including user interface, business logic, and data access layers --- are packaged and deployed as a single (Figure~\ref{fig:monolithic-architecture}), unified unit. In this model, the application runs as one process, often supported by a single codebase and a centralized database. \cite{thalor2024monolithic} describe monolithic systems as tightly coupled, meaning that changes in one part of the application often necessitate redeployment of the entire system.

The primary advantage of monolithic architecture lies in its simplicity. It is straightforward to develop, test, and deploy, making it particularly suitable for small teams and minimum viable products (MVPs). Since all components share the same memory space and runtime environment, monolithic applications also benefit from reduced communication overhead compared to distributed systems. This architecture enables rapid iteration during early development phases, where time-to-market and cost efficiency are prioritized.

\subsubsection{Domain Driven Design (DDD)}

Domain-Driven Design (DDD) is a software engineering methodology that integrates software architecture with the business domain to address the complexity of large-scale systems. Its primary objective is to ensure that software models accurately represent business processes, thereby shifting development from a technology-oriented to a domain-oriented perspective. \cite{ozkan2025ddd}

Two foundational concepts define DDD: Ubiquitous Language and Bounded Contexts. Ubiquitous Language is a collaboratively developed vocabulary shared between developers and domain experts. By embedding this language directly into communication and source code, DDD eliminates ambiguity and strengthens the alignment between the software model and the business domain. Bounded Contexts, in contrast, establish explicit boundaries around sub-domains, each maintaining its own model and terminology. This separation reduces complexity, prevents inconsistencies, and allows development teams to focus on smaller, coherent parts of the system.

Beyond conceptual clarity, DDD offers practical architectural benefits. The separation provided by Bounded Contexts naturally aligns with modern distributed paradigms such as microservices, where autonomous and loosely coupled services are essential. This approach enables systems to evolve alongside changing business requirements while maintaining technical robustness and strategic alignment with organizational goals. \cite{ozkan2025ddd}

\subsubsection{System Context Diagram}

The System Context Diagram is rooted in Structured Analysis and Design Technique (SADT). This methodology, developed in the 1970s, aimed to create a more disciplined approach to software development. The SCD is an integral part of Data Flow Diagrams (DFDs), where it serves as the top-level, or Level 0, diagram. \cite{paloalto2025dfd}

The theoretical underpinning is that by defining the system's boundaries and external interfaces first, developers can avoid getting bogged down in internal details too early. This aligns with the principle of separation of concerns, which advocates for breaking down a complex problem into smaller, more manageable parts. By isolating the system from its environment, the SCD allows for a clear focus on the system's external behavior before delving into its internal structure. This top-down approach ensures that the system being developed is relevant and responsive to the needs of its users and the environment it operates in.

\subsubsection{Codebase Structure}

A monorepo \cite{fernandez2024monorepo} is a single, unified version-controlled repository that houses a collection of logically distinct projects. This architectural paradigm contrasts with the traditional multirepo approach, where each project resides in its own separate repository. The primary advantage of a monorepo is the simplification of dependency management and a streamlined approach to code sharing across different applications, such as a web frontend and its corresponding API.

To address the performance challenges inherent in a large monorepo, namely slow build and testing times, the build system Turborepo \cite{turborepo2025intro} is employed. Turborepo operates on two key principles: content-addressable caching and parallel task execution. Content-addressable caching ensures that if the input to a build task has not changed, the build output can be instantly retrieved from a cache, eliminating redundant computation. Parallel task execution, in turn, leverages the inherent dependencies between projects to run independent tasks concurrently, maximizing the utilization of computational resources.

\subsection{Software Frameworks and Libraries}
\subsubsection{T3 Turbo Stack}
The T3 Turbo Stack \cite{t3app2025intro} is a modern full-stack development framework that unifies web development workflows by combining several powerful, opinionated tools into a cohesive environment. It provides a foundation that emphasizes type safety, developer productivity, and scalability. This stack serves as a model for efficient development workflows in contemporary software engineering. For a more comprehensive understanding of the T3 architecture, please refer to Figure~\ref{fig:t3-turbo-stack}.

\textbf{Core Components of the T3 Stack}
\begin{itemize}
  \item \textbf{Next.js:} A React framework for building fast, performant frontends. It handles complex setup like server-side rendering, routing, and API routes from a single codebase.
  \item \textbf{tRPC:} This library enables type-safe API communication between your client and server. It allows you to call backend functions directly from your frontend code, automatically inferring types. According to Vercel's documentation, this approach ``reduces the likelihood of integration errors while also ensuring maintainability across large applications.''
  \item \textbf{Tailwind CSS:} A ``utility-first'' CSS framework that lets developers build custom designs by composing pre-defined utility classes directly in their HTML.
  \item \textbf{Prisma:} An open-source database toolkit that provides a type-safe and intuitive way to interact with your database.
\end{itemize}

\textbf{Why the T3 Stack Matters}

The T3 Stack’s significance lies in its powerful combination of tools, which addresses common challenges in full-stack development. Its emphasis on type safety is a game-changer for mitigating runtime errors. By sharing types across the entire stack --- from the database (Prisma) to the API (tRPC) and the UI (Next.js with TypeScript) --- it prevents bugs that often arise from mismatched data.
Furthermore, the stack’s ``convention over configuration’’ philosophy greatly enhances developer productivity, allowing for quicker iteration and more efficient development. This streamlined workflow ensures that as an application scales, it remains highly maintainable and easier for new team members to work on.
